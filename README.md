# Go LRU Cache Evolution:  

Это репозиторий-исследование, посвященный эволюционному развитию алгоритма **LRU (Least Recently Used) кэша** на языке Go. 

Репозиторий представляет собой пошаговое решение инженерной задачи по разработке кэша

---

## Шаги Эволюции LRU

Проект разбит на изолированные пакеты, каждый из которых решает конкретную проблему предыдущих реализаций:

### V1: Base  
Классическая single-threaded реализация LRU-кэша. Абсолютно не потокобезопасен

### V2: Thread-Safe  
Обеспечение потокобезопасности «в лоб». Производительность упирается в конкуренцию за мьютекс

### V3: Sharded  
Масштабирование под конкурентную нагрузку методом сегментирования, каждый из которых защищен собственным мьютексом. Ранжирование происходит через равномерное ранжирование и хэширование ключа алгоритмами MurMurHash3Mix и FastRange. В тестах использована 64 битная версия алгоритма. Ниже результаты бенча на алгоритм

### V4: Container/List  
Замена самописного двусвязного списка функционалом пакета `container/list` из стандартной библиотеки Go

### V5: Generic  
Это v3 переписанный с использованием дженериков

### v6:
v5 + статистика. Показатели бэнча для v5, актуальны и для v6

---

### Хэширование и Ранжирование v3+

В качестве основного целевого решения распределения по шардам в проекте реализована 64-битная связка
1. **MurMurHash3 (Mix64-функция)** — обеспечивает быстрое распределение битов числового ключа (`int`), минимизируя коллизии.
2. **FastRange** — алгоритм отображения хэша в диапазон индексов шардов без использования операций деления

Замеры производительности проводились для валидации выбранного 64-битного подхода. Тесты для 32-битных чисел, строк и стандартного оператора остатка от деления (`%`) приведены справочно для сравнения:

| Бенчмарк | Итерации | Скорость (ns/op) | Память (B/op) | Аллокации | Статус / Назначение |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **BenchmarkFor64_Dynamic** | 1 000 000 000 | **1.421 ns** | 0 B | 0 | MurMurMix64 + FastRange |
| **BenchmarkStandardMod64_Dynamic** | 1 000 000 000 | **1.426 ns** | 0 B | 0 | Стандартный оператор `%` (Mod) |
| **BenchmarkFor32_Dynamic** | 1 000 000 000 | **1.231 ns** | 0 B | 0 | 32-битный вариант MurMurMix + FastRange |
| **BenchmarkForStr_Short** | 557 621 421 | **6.502 ns** | 0 B | 0 | Хэширование коротких строк |
| **BenchmarkForStr_Long** | 95 786 968 | **36.860 ns** | 0 B | 0 | Хэширование длинных строк |

*Выводы:*

* Выбранная связка `MurMurHash3Mix64` + `FastRange` выполняется всего за **1.42 наносекунды** с нулевыми аллокациями. По скорости она не уступает аппаратной инструкции деления, но гарантирует равномерное распределения ключей по шардам. Это полностью защищает структуру от дисбаланса и деградации при направленных нагрузках, что подтверждается тестом `ShardSkewer_HashAttack` в общих бенчмарках. Использование шардирования по остатку от деления недает никаких преимуществ
* Использование 32 версии даст еще немного производительности если ключи позволяют укладываться в 32 бита, но повысит шансы поймать коллизию.
* Строковые ключи для доступа к кэшу с этими алгоритмами требуют значительно больше ресурсов и зависят от размера ключей

### Паттерны нагрузки:

**Uniform ReadHeavy 10/90**:  
Равномерное случайное чтение. Запросы идут случайно по всей базе ключей. 90% операций — это чтение, 10% — запись. Горячих ключей нет.  
**Метрики LRU**: `itemsCount=96000; hit=135922584; miss=136454811; del=15067759; upd=15100086; HitRate=0.50; MissRate=0.50`

**Pareto 80/20**:  
80% всех запросов бьют по 20% самых популярных ключей.  
**Метрики LRU**: `itemsCount=96000; hit=214693823; miss=30910068; del=7634106; upd=53677987; HitRate=0.87; MissRate=0.13`

**Zipfian Web Traffic**:  
Симуляция веб-трафика. Есть несколько «супер-хитов» (например, главная страница), которые генерируют почти весь поток запросов, а остальные смотрят редко.  
**Метрики LRU**: `itemsCount=96000; hit=215743012; miss=8119104; del=806632; upd=23976538; HitRate=0.96; MissRate=0.04`

**OneHitWonders CacheWash**:  
Атака одноразовыми ключами. Полезные данные вымываются мусором.  
**Метрики LRU**: `itemsCount=96000; hit=32624931; miss=76127071; del=76020326; upd=32617282; HitRate=0.30; MissRate=0.70`

**Thundering Herd**:  
 Конкуренция за один ключ. Горутины пытаются прочитать и обновить один и тот же небольшой набор ключей из-за чего возникает сильная конкуренция за доступ к кэшу.  
**Метрики LRU**: `itemsCount=43943; hit=94164398; miss=835494; del=0; upd=4956165; HitRate=0.99; MissRate=0.01`

**SequentialScan Backup Imitation**:  
Имитация работы бэкапа или выгрузки - последовательный перебор данных. Элементы читаются по одному разу, постоянно выбивая данные из кэша. Кэш должен уйти в бесконечные промахи и удаления.
**Метрики LRU**: `itemsCount=96000; hit=0; miss=137592723; del=137496723; upd=0; HitRate=0.00; MissRate=1.00`

**MovingHotspot TrendShift**:  
Сценарий, при котором меняются тренды. Одна популярная группа данных, заменяется другой группой. Показывает способность кэша переобучатся
**Метрики LRU**: `itemsCount=96000; hit=164929774; miss=29893123; del=3225118; upd=18318827; HitRate=0.85; MissRate=0.15`

**ShardSkewer HashAttack**:  
Намеренная генерация ключей кратных количеству шардов. При плохом распределении данные попадают в один шард и перегружают его
* **Метрики LRU**: `itemsCount=6000; hit=317875657; miss=23313; del=0; upd=79471707; HitRate=1.00; MissRate=0.00`

---

### Выводы:
1. В конкурентных сценариях `Uniform`, `Pareto`, `Zipfian` переход от глобального мьютекса к сегментированию значительно снижает накладные расходы
2. Использование стандартного связного списка делает код лаконичнее, но накладывает небольшой штраф на производительность и генерирует паразитные аллокации.
3. LRU показывает высокий HitRate на «горячих» данных и хорошо показывает себя в сценариях `Pareto`, `Zipfian`, `Thundering Herd`, `MovingHotspot TrendShift`
4. LRU абсолютно не защищен от вымывания полезных данных при кэшировании большого числа одноразовых ключей. Кэш не устойчив к сценариям `SequentialScan`, `OneHitWonders`, `Uniform ReadHeavy 10/90` 
5. MurMurMix + FastRange быстро и равномерно распределяют ключи, позволяя избежать `ShardSkewer HashAttack`
