# Go LRU Cache Evolution: От Базовой Структуры до Высококонкурентного Generic-Решения

Это репозиторий-исследование, посвященный эволюционному развитию алгоритма **LRU (Least Recently Used) кэша** на языке Go. 

Репозиторий представляет собой пошаговое решение типичной инженерной задачи, на примере которой наглядно демонстрируется, как требования к конкурентности, производительности и типизации меняют архитектуру кода, внутренние структуры данных и итоговые метрики в бенчмарках.

---

## 🚀 Шаги Эволюции LRU

Проект разбит на изолированные пакеты, каждый из которых решает конкретную проблему предыдущих реализаций:

### 📦 V1: Base
* **Идея**: Классическая single-threaded реализация LRU-кэша.
* **Структуры**: Хэш-таблица (`map`) для быстрого O(1) поиска и кастомный двусвязный список для упорядочивания и вытеснения элементов.
* **Ограничение**: Абсолютно не потокобезопасен

### 🔒 V2: Thread-Safe
* **Идея**: Обеспечение потокобезопасности «в лоб».
* **Решение**: Поверх базовой структуры V1 добавлен глобальный мьютекс (`sync.RWMutex`), блокирующий весь кэш на любую операцию чтения или записи.
* **Ограничение**: При увеличении количества процессорных ядер производительность упирается в жесткий **Lock Contention** (конкуренцию за мьютекс).

### ⚡ V3: Sharded
* **Идея**: Масштабирование под конкурентную нагрузку методом сегментирования.
* **Решение**: Пространство ключей разделено на независимые сегменты (шарды), каждый из которых защищен собственным локальным мьютексом. Поиск шарда происходит через равномерное ранжирование и хэширование ключа алгоритмами MurMurHash3Mix и FastRange. В тестах использована 64 битная версия алгоритма. Ниже результаты бенча на алгоритм
* **Результат**: Кардинальное снижение Lock Contention. Кэш отлично утилизирует многоядерные процессоры.

### 🧩 V4: Container/List
* **Идея**: Эксперимент по упрощению кодовой базы.
* **Решение**: Замена кастомного двусвязного списка стандартным пакетом `container/list` из стандартной библиотеки Go.
* **Вывод исследования**: Стандартный контейнер делает код чище, но добавляет **накладные расходы на аллокации и снижает скорость**. Архитектурный тупик для highload-решений.

### 💎 V5: Generic
* **Идея**: Бескомпромиссная производительность + Type Safety времени компиляции.
* **Решение**: Полный отказ от идей V4 в пользу максимальной производительности. Версия v5 это v3, переписанная с использованием **Go Generics**.
* **Результат**: Нулевые аллокации памяти, сохранение преимуществ шардирования и строгой статической типизации без интерфейсов и type assertion.
* **Ограничение**: Хранит значения в пустых интерфейсах (`interface{}` / `any`), требуя постоянного приведения типов в рантайме.


Все тесты производились на следующей конфигурации:
* **ОС/Архитектура**: Windows / amd64
* **Процессор**: AMD Ryzen 5 7500F 6-Core Processor (12 потоков)
* Длительность каждого теста 3 секунды

### 🎯 Оптимизация шардирования v3+: Хэширование и Ранжирование

В качестве основного целевого решения распределения по шардам в проекте реализована универсальная 64-битная связка
1. **MurMurHash3 (Mix64-функция)** — обеспечивает быстрое и лавинообразное распределение битов числового ключа (`int`), минимизируя коллизии.
2. **FastRange** — алгоритм отображения хэша в диапазон индексов шардов без использования деления

Замеры производительности проводились для валидации выбранного 64-битного подхода. Тесты для 32-битных чисел, строк и стандартного оператора остатка от деления (`%`) приведены справочно для сравнения:

| Микро-бенчмарк | Итераций | Скорость (ns/op) | Память (B/op) | Аллокации | Статус / Назначение |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **BenchmarkFor64_Dynamic** | 1 000 000 000 | **1.421 ns** | 0 B | 0 | MurMurMix64 + FastRange |
| **BenchmarkStandardMod64_Dynamic** | 1 000 000 000 | **1.426 ns** | 0 B | 0 | Стандартный оператор `%` (Mod) |
| **BenchmarkFor32_Dynamic** | 1 000 000 000 | **1.231 ns** | 0 B | 0 | Альтернативный 32-битный вариант MurMurMix + FastRange |
| **BenchmarkForStr_Short** | 557 621 421 | **6.502 ns** | 0 B | 0 | Хэширование коротких строк |
| **BenchmarkForStr_Long** | 95 786 968 | **36.860 ns** | 0 B | 0 | Хэширование длинных строк |

*Выводы:*

* Выбранная связка `MurMurHash3Mix64` + `FastRange` выполняется всего за **1.42 наносекунды** с нулевыми аллокациями. По скорости она не уступает аппаратной инструкции деления, но гарантирует равномерное распределения ключей по шардам. Это полностью защищает структуру от дисбаланса и деградации при направленных нагрузках, что подтверждается тестом `ShardSkewer_HashAttack` в общих бенчмарках. Использование шардирования по остатку от деления недает никаких преимуществ
* Использование 32 версии даст еще немного производительности если ключи позволяют укладываться в 32 бита, но повысит шансы поймать коллизию и разные ключи будут чаще попадать в один шард.
* Строковые ключи для доступа к кэшу с этими алгоритмами требуют значительно больше ресурсов и зависят от размера ключей

### 💡 Ключевые выводы по результатам анализа
1. **Проблема Lock Contention преодолена**: В конкурентных паттернах чтения/записи (`Uniform`, `Pareto`, `Zipfian`) переход от глобального мьютекса (`V2`) к сегментированию (`V3`, `V5`) снижает накладные расходы **в 5–7 раз**.
2. **Накладные расходы `container/list` (V4)**: Использование стандартного связного списка делает код лаконичнее, но накладывает небольшой штраф на производительность и генерирует паразитные аллокации.
3. **Универсальное дженерик решение**: По причине неэффективности `container/list`, дженерик-версия V5 была на базе V3. Это позволило сохранить нулевые аллокации памяти (`0 B/op`) и максимальную пропускную способность, добавив строгую статическую типизацию времени компиляции. В целом использование решение с дженириком в кэше добавляет минимум расходов, но предоставляет значительно большую универсальность для эффективного обслуживания любых типов данных во всем приложении, сохраняя строгую типизацию на этапе компиляции
